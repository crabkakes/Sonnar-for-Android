# Sonarr Mobile — native app design

Date: 2026-10-30
Status: draft, awaiting approval

## Intent

Sonarr's web UI is built for computers and doesn't fit a phone screen at all. This replaces the earlier version of the app (a React web app packaged as a PWA/TWA, with an Express proxy), which didn't meet these goals. The replacement is a native app for iPhone and Android that lets someone manage their Sonarr from their phone: the shows they've added, adding new ones, downloads, and what's airing.

Who it's for: the owner (an iPhone user), their friend (Android), and anyone with an Android phone or iPhone and Sonarr on a home server.

**Success:** it works well on the owner's iPhone and is clearly better than using Sonarr's web UI on a phone.

## Goals

- Phone-first UI, built for one-handed use, that also scales sensibly to tablets and foldables.
- Shows, show detail, add show, calendar, activity (queue + history), and manual (interactive) release search.
- Talks **directly** to the user's Sonarr over the local network. No server of ours anywhere.
- Ships on the Google Play Store, the Apple App Store, and as a free APK on GitHub releases.
- A clearly labeled **sample-data mode** so store reviewers (and curious users) can explore every screen without a Sonarr. See below.

## Non-goals (this build)

- Sonarr settings. The only configuration is the connection (URL + API key).
- Notifications and background work of any kind. The app only knows things while it's open.
- Multiple Sonarr servers.
- A simulated status bar, PWA/browser install, TWA/Bubblewrap packaging.
- Other *arr apps (Radarr, etc.).
- Remote access outside the home network/VPN.

## Anti-goals

- **Any server in the middle.** No proxy, no backend, no relay, no cloud service that sees requests or API keys. Expo's cloud services (EAS Build, EAS Update) aren't used, and builds are made locally or in GitHub Actions.
- Analytics, tracking, crash reporting that phones home, or accounts.
- A desktop layout squeezed onto a phone.
- Paywalls or differences between the store builds and the free APK.

## Constraints

- **Platform/stack: React Native with Expo, TypeScript.** Chosen so the owner can test on their iPhone with Expo Go during development, and one codebase ships to both stores. (The owner considered Kotlin and would only switch to Android-only if Expo required a server, which it doesn't.)
- **Network:** the phone only ever reaches Sonarr on the local network, either at home or over a VPN (e.g. WireGuard, Tailscale). Addresses will typically be plain `http://` to a LAN IP or hostname (e.g. `http://192.168.1.50:8989`), sometimes `https://` behind a reverse proxy.
  - Android must allow cleartext HTTP.
  - iOS App Transport Security must allow plain HTTP to arbitrary user-entered hosts. That covers LAN IPs and `.local`, but also VPN hostnames such as Tailscale MagicDNS names, which `NSAllowsLocalNetworking` alone doesn't cover. The builder decides the exact ATS keys, and whatever is chosen needs an App Store review justification (a user-configured self-hosted server).
  - iOS will show the Local Network permission prompt, so it needs a clear usage description string.
  - Self-signed HTTPS certificates are out of scope for this build. If the TLS handshake fails, show a clear error explaining it.
- **Sonarr versions:** v3 and v4 (both expose `/api/v3`). If the server isn't Sonarr or is an unsupported version, say so plainly.
- **Auth:** the API key is sent in the `X-Api-Key` header. It's stored in the platform's secure storage (Keychain/Keystore), never in plain storage or logs.
- **Distribution:** Play Store, App Store, and a signed APK attached to GitHub releases, all the same version. The owner has both store accounts. The project must produce store-ready builds and document the release steps. TestFlight is available for iPhone beta testing.
- **Builds:** the owner has a Mac, so iOS builds (dev builds, TestFlight, App Store) are made locally on it with Xcode/Expo's local tooling. Android builds can be made on Linux or in GitHub Actions.
- **Android signing:** the GitHub APK and the Play Store build use **one shared signing key**, generated by us and uploaded to Play App Signing before the first release, so users can move between the two without reinstalling. The key and its passwords live outside the repo (CI secrets + an offline backup), and the release docs say so.
- **Testing on device:** Expo Go is fine for everyday UI work on the owner's iPhone, but it doesn't use this app's Info.plist/ATS, Local Network string, or Keychain config. Networking to a real Sonarr, permissions, and secure storage must be verified in a development build or TestFlight build on the iPhone.

## The app

Bottom tabs: **Shows · Calendar · Activity**, plus a way to reach the **Server** screen (connection). The visual direction comes from the brainstorm wireframes: dark and light themes following the system setting, posters, clear progress bars.

### First run / Server
- Enter the Host URL and API key, then **Test**, then save.
- Errors must be useful to a stranger setting this up alone: wrong URL or port, not reachable (offer "are you on your home network or VPN?"), wrong API key, not Sonarr, TLS failure.
- Later, the same screen lets you edit or replace the connection. It holds no other settings.

### Shows
- Your series list with poster, title, and a status line (episode counts like `14/18`, next airing, missing count, ended), plus a progress bar.
- Search/filter your shows. A **+** button opens Add.
- Pull to refresh.

### Show detail
- Header with poster/fanart, monitored state, quality profile, season count.
- Season sections you can expand, with episodes and their status (downloaded with quality, missing, not aired yet with date).
- Actions: search an episode automatically, search a whole season automatically, **pick a release** (interactive search) for an episode or season, toggle monitoring for the series/season/episode, and delete the series (with an option to delete files, behind a confirmation).

### Add show
- Search by name through Sonarr's lookup, which Sonarr runs (the app doesn't call TVDB/SkyHook itself).
- Pick a result, then set the root folder, quality profile, monitor option, series type (Standard/Daily/Anime), and "start search for missing episodes." The option lists come from the user's Sonarr, and the last choices are remembered as defaults.
- Already-added shows are marked in the results.

### Calendar (chosen: week strip + day)
- A row of days across the top that you swipe week by week, with a dot on days that have episodes. Opens on today.
- Tap a day to list its episodes: poster, show, `SxxEyy`, title, air time in the device's time zone, and status (downloaded, missing, upcoming).
- Tapping an episode goes to that show's detail.

### Activity
- **Queue:** each item shows title, episode, quality, progress, size, speed/time left where Sonarr provides it, and status. Warnings and errors from Sonarr (stalled, import failed, etc.) are shown plainly. It refreshes while on screen.
- Actions per item: **Remove** and **Remove + block this release** (blocklist), each with optional "remove from download client." Note: Sonarr's API has no pause/resume for download client items, so the old app's claim to support it doesn't carry over.
- **History:** a timeline of grabbed, imported, failed, and deleted events, newest first, loaded as you scroll.

### Interactive search (chosen: short rows, tap for more)
- Opened from an episode or season in Show detail.
- A list of releases from Sonarr's release search, in Sonarr's own order by default. Quick filters across the top: quality (e.g. 1080p, 2160p), hide rejected, and sort (Sonarr's pick, size, seeders, age).
- Each row shows quality, size, seeders/peers (torrents), and release group. Rejected releases are dimmed with a warning mark.
- Tapping a row expands it with the full release name, indexer, age, language, and **rejection reasons**, plus a **Grab** button. Rejected releases can still be grabbed after a confirmation.
- Release searches can take a while, so show progress and let the user back out.

### Sample-data mode
- Offered on the first-run Server screen ("Explore with sample data") and reachable again from the Server screen.
- Uses bundled fixture data (the same fixtures the tests use) to fill every screen: shows, detail, add search results, calendar around today's date, an active queue with a stalled item, history, and interactive search results.
- Always clearly marked as sample data (e.g. a persistent banner). Actions do nothing real and say so. It never mixes with a real connection.
- Store review notes tell reviewers to use it.

## General behaviour

- Phone-first layouts, sized for one thumb, with big tap targets and primary actions within easy reach. On wider screens, layouts use the space (e.g. more poster columns, list + detail side by side) instead of stretching.
- Fast and responsive: cache the last-loaded data so screens open instantly, then refresh.
- If Sonarr is unreachable, say so on screen (likely off the home network or VPN) and keep showing the cached data, marked as stale.
- Poster images come from the user's Sonarr (its media cover endpoints), with auth. Anything else the builder settles.

## Repo

The work happens on a new branch and lands as a pull request. The new app replaces the existing React/Express code in this repo (the old code is removed in that PR, with git history keeping it).

## Left to the builder

- Project layout, navigation library, state/data-fetching approach, and component library (if any). Keep dependencies lean.
- Exact visual design within the direction above, the icon, and the app name (it must not use Sonarr's logo in a way that implies it's official).
- Refresh intervals, caching details, and pagination sizes.
- The test strategy, which must include unit tests for the API client/data mapping and be runnable without a real Sonarr (fixtures). The owner verifies on their iPhone via Expo Go.
- The CI workflow for building the signed APK and attaching it to GitHub releases, plus documenting store submission steps.

## Calls made by Claude (not explicitly decided by the owner)

- Expo, building locally or in GitHub Actions, and no EAS Build or EAS Update.
- Support for Sonarr v3 + v4.
- The API key kept in secure storage.
- Dark/light theme following the system.
- Delete series and monitoring toggles included in Show detail.
- Remembered defaults in Add.
- Self-signed HTTPS out of scope.
- Sample-data actions do nothing real (no fake state changes).
